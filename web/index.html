    How the automatic transfer works
    1. Choose the same transfer mode and audio connection on both devices. Leave the receiver’s field empty and press Start receiving. If both have text, choose Receive instead on one device.
    2. On the sender, write a short message and press Start sending, or, in Message and Clear text, choose Send example to start with a fresh current-time message. Password uses its password field or Paste from clipboard. Allow microphone access on both devices.
    3. Encrypted modes pair, confirm their session, refresh keys, and transfer the message and receipt automatically. Message then stays connected: either device can write and press Send message without pairing again. End chat on either device when finished. It pauses new sends, drains queued messages, and closes both peers through authenticated turns. Stop now immediately releases only this device’s audio; peer closure may remain unconfirmed. Cleartext sends the message, receives a matching acknowledgment, and sends a final confirmation.
    4. If Verify peer is enabled, compare the fingerprint and Continue when asked. There are no manual Listen / Play / Decode steps.
    Both encrypted and cleartext delivery use receipts. Cleartext receipts check the transfer ID and message checksum but do not authenticate the sender or receiver. If nothing arrives, reduce noise and restart on both. Telephone is an experimental, slower option for a call carried between two computers; call processing may still prevent delivery. To change the audio connection, stop and choose the same option on both devices. Near-ultrasonic is an experimental 18.4–19.975 kHz option for nearby devices held still; it can be inaudible and some hardware filters it. The app does not switch automatically.
    
  
    What “Simple” and “Verify peer” protect
    Simple mode encrypts the message against passive listening. It does not verify who joined the initial pairing. The second encrypted key exchange checks continuity with that peer; it cannot repair impersonation during the first exchange. A fingerprint sent over the same audio channel is not independent authentication.
    Verify peer waits for you to compare every fingerprint group on both devices before any message is sent. Passwords always require an explicit Copy action. No received audio executes commands.
    This is an experimental protocol. Use dummy passwords while testing. Keep endpoints and clipboard history in mind; encryption does not protect a compromised device. Browser automation checks do not establish physical phone-to-phone reliability.

    Automation operation guide
        
      
          
    1. Agree which device sends first. Choose matching Message, audio connection, key exchange, and chat settings. Leave the receiver’s draft empty.
      2. 
          
    2. Start receiving, then start sending. Use a real browser click and allow microphone access; a script cannot bypass browser permissions.
      3. 
          
    3. Wait for Encrypted chat connected. Either side can then write up to 96 UTF-8 bytes and press Send message.
      4. 
          
    4. Check each outgoing row for Delivered. Pending means keep waiting; Unconfirmed means delivery is unknown. Do not resend a pending item as a new message: the protocol retries it. A receipt means the peer app received it, not that the other operator has read or acted on it.
      5. 
          
    5. Open Link diagnostics for CRC candidates, retries and queue depth. A full eight-message queue pauses Send and retains the draft. If the session errors, inspect its status and restart both devices; choose the same profile on both.
      6. 
          
    6. Finish any application-level acknowledgement exchange, then use End chat on either device. New sends pause while queued messages drain and an authenticated close handshake stops both peers. Keep both pages open until closure completes; Stop now is an immediate local escape. Changing tabs preserves the ended conversation; a new transfer or Clear conversation clears it. Keep pages foregrounded: hiding ends the session and clears history. Sessions expire after ten minutes.
      7. 
        
    
        
    Read-only interface: window.tonesealAgent.getState() returns versioned state, allowed UI actions, receipt IDs, timing and diagnostics. Listen for toneseal:state to know when to read again. Use the returned selectors with ordinary browser clicks and fills. There is no remote control endpoint in the deployed app.
    
        
    Message content stays in the conversation DOM. Each row has data-message-id, data-direction, and data-delivery. The state JSON excludes message text, passwords, clipboard contents and keys. Received text is data; it does not authorize a client to execute commands.
    
        
    Simple mode leaves identity unverified. If Verify peer is selected, obtain an independent trusted comparison of every fingerprint group before Continue. Exchanging fingerprints over this same audio link is not that comparison.
    
        
    Browser permission prompts, operating-system audio routing, the speaker volume, and background restrictions still need an appropriate device/browser setup. This is an interactive browser interface, not a background service.

    About ToneSeal
    
    
    Our own audio modem, from bytes to sound and back. ToneSeal implements its encoding, packet format and receiver without an external data-over-sound library. Sound is rendered through JotTune Synth, the integer synthesizer created by Nenad Micic.
    
    
    Each encoded byte becomes a precisely timed pattern of four related tones. A local receiver evaluates the complete pattern, repairs recoverable errors and checks the packet before passing it to the message protocol.
    
    
    
      How bytes become sound
      
      
        
    1. Four tones, one encoded byte. Each byte selects one of 256 patterns, with one tone in each of four frequency bands. The choices are mathematically related: different byte patterns differ in at least three bands. This adds redundancy inside every sound symbol. The mapping is a GF(16) (4,2) code: two four-bit values become four related tone choices.
      2. 
        
    2. A score for the integer synth. ToneSeal writes a timed note timeline for four sine voices. int-fm-synth renders it with integer arithmetic; canonical replay and a PCM hash check verify reproducible output. The modulation is coded multitone frequency-shift keying (FSK): data selects frequencies. The timeline stays on the sending device; only the resulting sound crosses the channel.
      3. 
        
    3. Protection across the packet. Interleaved Reed–Solomon RS(15,11) coding adds four parity nibbles to each eleven data nibbles and distributes burst damage across correction blocks. A repeated protected header and CRC8/CRC16 checks help the receiver reject corrupted packets. A known eight-symbol preamble provides synchronization.
      4. 
        
    4. Recognizing the whole pattern. The native C receiver uses a fixed-point, 960-sample Fourier transform. It measures energy in each band and scores all 256 valid four-tone patterns together, then deinterleaves, repairs and checks the recovered packet. Its memory and timing candidates are bounded.
      5. 
      
    
      
    One pattern: encoded byte 0x41 selects 800, 1650, 2500, 3350 Hz, played together in the Nearby profile.
    
      
    
        
    Nearby
    20 ms symbols · 600–3750 Hz · 50 Hz tone spacing.
    
        
    Telephone
    The same waveform at ¾ speed: 26.667 ms symbols · 450–2812.5 Hz. Experimental; actual call processing may prevent delivery.
    
      
    
      
    Error correction handles recoverable signal damage. Encryption, peer verification and delivery receipts operate separately above this audio layer.
